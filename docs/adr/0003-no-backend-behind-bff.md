# ADR 0003: BFF の背後にバックエンドを置かず、BFF をサーバー側の唯一のアプリケーションとする

- ステータス: Accepted
- 日付: 2026-10-28
- 関連: [ADR 0001](./0001-authentication-provider.md)、[ADR 0002](./0002-session-strategy.md)

## コンテキスト

ganana-bff は BFF（Backend For Frontend）として、web フロントエンド（ganana-web）と iOS アプリの双方を担う。

これまでのドキュメント（README / architecture.md）は、BFF の背後にコア（勘定系など重いドメイン）を担う別のバックエンドが存在することを暗黙の前提とし、BFF を「エッジレイヤーとして薄く保つ」と記述していた。また役割として「複数 API の集約・オーケストレーション」を挙げていた。

しかし、**BFF より後ろ（コアとなるバックエンドサービス群）を作ることは現時点では考えていない**。前提と実態がずれたままだと、存在しないバックエンドへの委譲を想定した設計判断や、薄さを保つための不要な抽象化を招くおそれがあるため、方針を明文化する。

## 決定

**BFF の背後に独立したバックエンドサービスを置かない。ganana-bff を Ganana におけるサーバー側の唯一のアプリケーションとする。**

```
web（ganana-web） ─┐
                   ├──▶ ganana-bff ──▶ 外部サービス（Supabase など）
iOS アプリ ────────┘
```

これに伴い、BFF の責務を次のとおり改める。

- **ドメインロジックは BFF 自身が持つ**。「重いドメインは別のバックエンドに置く」という前提は撤回する
- **BFF が直接呼び出すのは外部サービスのみ**（現時点では Supabase Auth）。自前のバックエンド API を集約する役割は持たない
- データストアが必要になった場合は、**BFF が直接アクセスする**。具体的な選定は必要になった時点で ADR を起こす（ADR 0001 は Supabase の Postgres を一本化の候補として挙げている）

名称と、フロントエンド向けに最適化した API を提供するという位置付けは変えない。

## 理由

- **YAGNI**: 現時点の要件に、BFF と分離したバックエンドを必要とするものがない。サービスを分ければデプロイ・監視・サービス間認証などの運用対象が増えるが、それに見合う利点がまだない
- **実態との整合**: 存在しないバックエンドを前提にした記述を残すと、設計・レビュー時の判断を誤らせる

## 影響

### 利点

- サーバー側の運用対象が ganana-bff 1 つに限られる
- サービス間通信・サービス間認証の設計が不要

### 欠点・留意点

- 「BFF は薄い」という前提が成り立たなくなる。ドメインロジックが増えるにつれ、BFF のコード量と責務は大きくなる
- 将来バックエンドを切り出す場合の移行コストを抑えるため、HTTP ハンドラ（画面向けの整形）とドメインロジックは別パッケージに分けて実装する。ただし切り出しを見越した抽象化（サービス間通信を模したインターフェース等）は先回りして作らない

## 見直しの条件

次のいずれかが生じた場合、本 ADR を見直し、バックエンドの分離を検討する。

- BFF 以外のクライアント（バッチ、他システム、外部公開 API 等）から同じドメインロジックを利用する必要が出た
- 特定のドメイン処理だけを独立にスケール・デプロイする必要が出た
- ドメインロジックの肥大化により、単一アプリケーションとしての保守が困難になった
